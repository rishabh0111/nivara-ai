# Reranking runs inside Qdrant, because the deployed instance has a tenth of a core

The conventional second stage of a retrieval pipeline is a cross-encoder run locally: fetch fifty candidates, score each against the query, keep the best five to ten. It is reported as the largest single jump in recall, small rerankers are cheap, and the plan for this service assumed the only question was whether one would fit in memory.

**Memory was the wrong constraint.** The deployed instance is 512 MB and **0.1 vCPU**. Scoring fifty query–chunk pairs on a tenth of a core is seconds of latency on the path to first token, and it competes for that same tenth with the ONNX query embedder, which must also run per request. A reranker that turns a two-second answer into an eight-second one has not improved the product, whatever it did to recall@5.

**So the rerank moves server-side.** Qdrant's Query API takes a `prefetch` of candidates and rescores them with a late-interaction multivector in the same call — the documentation's own example fetches a hundred with a dense vector and rescores to the top ten — so hybrid retrieval and reranking are one round trip and the per-pair arithmetic happens on Qdrant's hardware rather than on ours. What stays local is encoding the *query* into multivectors, which is a fraction of the work of scoring fifty pairs against it.

This also strengthens the choice of Qdrant rather than sitting awkwardly beside it. The store was chosen because recall engineering — HNSW parameters, quantisation, fusion — is the skill worth demonstrating and none of it exists when the retriever is a dot product. Reranking is now on that same surface.

The cost accepted is index size. Late-interaction vectors are per token, which inflates storage against a free tier of roughly 1 GB RAM and 4 GB disk, so the corpus must be measured against that ceiling early rather than at the end. If it does not fit, the fallback is not a local cross-encoder — it is shipping hybrid with fusion only and **reporting what reranking bought and what it would have cost**, which is a better answer to *"under what conditions would you ship it"* than an unexamined yes.

The local cross-encoder does not disappear; it stays as a row in the ablation table, run in CI where CPU is real. The table is then able to say something most cannot: not merely which configuration retrieves best, but which configuration retrieves best *on the hardware this is actually deployed to*.

**Measured (ticket 11).** The late-interaction encoder is `answerdotai/answerai-colbert-small-v1`, 96 dimensions per token. Over the 240-chunk Corpus that is ~16.8k token-rows and ~6.4 MB of raw vector data; the Qdrant collection is 17.8 MB on disk with all three vector types, and the process holds under 200 MB resident. Against the ~1 GB / ~4 GB ceiling this fits with room, so the fallback above is not triggered. `scripts/measure_index.py` reproduces the numbers from the compose Qdrant. Server-side per-query IDF corpus and the nested rerank prefetch both require Qdrant 1.19, which is now the compose image and the client floor.

**Ablated (ticket 12) — and the rescore is now off by default.** This ADR decided reranking runs *server-side rather than locally*; it assumed reranking. `eval/retrieval_ablation.md` tested that assumption, running the late-interaction rescore as its own row against the 550-question labelled set. It does not improve retrieval: −1.6 pp recall@1, −0.008 MRR against the hybrid fusion it rescores, recall@5 already saturated at ~99%. The local cross-encoder alternative this ADR keeps as a row is no better and ~100× the latency (on a host faster than the deployed instance), so the server-vs-local *shape* of this ADR still holds — it just no longer has a stage to apply to on the default path.

Decision 27a is explicit: a stage that does not move the number is deleted and its row kept. So **`Retriever(rerank=…)` now defaults to `False`** and the deployed query is hybrid fusion with no rescore. What stays: the constructor toggle, the ablation row, and the late-interaction multivector on every indexed point. Two reasons the index stays rather than being reclaimed now — an 80-document Corpus with saturated recall@5 cannot show whether a rescore helps a harder one, and ticket 16 plans to read the post-rerank margin as a Gate Free signal, a product use independent of recall. If ticket 16 does not use the margin and the Corpus does not grow, a follow-up drops the multivector index and the resident late-interaction encoder (~158 MB) as well.

**Resolved (ticket 16).** The Gate reads the post-rerank margin as one of its three Free signals (`nivara_ai.gate.signals`, ADR-0008), so the contingency above does not fire: the multivector index and the resident encoder stay for that product use, independent of the reranking stage being off.
