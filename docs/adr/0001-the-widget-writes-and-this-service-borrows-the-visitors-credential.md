# The Widget writes the customer's words, and this service reads them with the Visitor's own credential

The obvious arrangement is that the Widget posts a message to this service, and this service does everything else — opens the Ticket, records the customer's message, answers. It is one call from the browser and one place where conversation logic lives. It is wrong twice, and the second way is a vulnerability rather than an inelegance.

**The first problem is authorship.** `conversation_stamp_author()` sets a Message's `author_kind` and `author_id` from the actor armed on the transaction, taken from the presented credential — not from anything the caller sends. A Message this service writes is `service`-authored by Postgres whatever the request claims. So if this service recorded the customer's own words, the customer would be stamped as the machine. Deflection counts terminal Tickets with **no user-authored Message or Note**, which means every conversation would qualify by construction, and the one number in this project computed by a system that does not answer to it would become a number this service had quietly rigged. The Widget already opens Tickets and posts Messages as the Contact, over `POST /widget/tickets` and `POST /widget/tickets/:id/messages`, authorized by principal *kind*. **So the Widget keeps doing exactly what it does today**, and this service is handed a Ticket id.

**The second problem is that a Ticket id from a stranger is not authority to read it.** This service is a public endpoint — an anonymous browser on somebody else's website calls it — and it holds a service token whose reach is the whole Tenant. Row-level security does not narrow that: the policies on `message` and `note` are Tenant-scoped, and the conversation migration says so in as many words, that they *"cannot tell a Contact from a User"*. A service that accepted a Ticket id and read it with its own credential would answer questions about any Conversation whose id could be guessed or scraped, and would read another Visitor's support thread back out in prose. That is a confused deputy, and no amount of prompt hardening addresses it, because the model would be behaving perfectly.

**So the Widget forwards its own `nvw_` session token, and this service reads the Conversation and its thread with that** — a **Borrowed read**. A Ticket that is not that session's answers `404`, identically to one that does not exist, from the same code path that answers a Visitor directly. The service token is used only for the writes the Visitor genuinely cannot perform: the reply, the Note, the transition.

The alternative considered was to forward the session token as *proof* only — check ownership once against `GET /widget/tickets/:id`, then read everything with the service token. It was rejected because it turns a structural property into a procedural one. A check can be forgotten by a code path added later; a credential that never had the reach cannot be. The distinction is the whole argument this repository makes about safety, and applying it to ourselves rather than only to the model is the least we can do.

The cost accepted is that the two ingresses are genuinely different. The **Slack ingress** has no Visitor and no forwardable credential — its work is queued and drained inside the API, with no browser anywhere — so it reads with the service token, and that is the *only* reason `ticket:read` appears on the Assistant token at all. If Slack were dropped, the token would fall to three scopes. That is worth knowing rather than discovering: a surface added for reach widened the credential, and the honest place to record it is here.
