# The Tenant boundary is enforced at the retrieval layer, and that includes the IDF population

The hard constraint on this service is that it holds no credential to the Nivara Desk database. Tenant isolation there is a property of Postgres row-level security beneath a non-`BYPASSRLS` role, and the way to keep it not our problem is to be unable to connect.

**But the vector store sits outside that database, and the boundary moved with it.** Whatever the Corpus is derived from, the index is ours, and the database can no longer be the thing that stops a cross-tenant read. So the same guarantee has to be re-established here, and stating that precisely is the point: the constraint forbids a credential to *the helpdesk database*, and this service does hold one to its own retrieval store. A constraint understood well enough to say exactly what it forbids — and to notice where it has moved a boundary that now needs defending — is worth more than one applied superstitiously.

**Concretely, one collection partitioned by a Tenant payload index, with the filter injected server-side at the retrieval layer**, resolved once at the edge from the credential and never from a message, a tool argument, or anything a model produced. A retrieval-layer test asserts that a query issued for one Tenant cannot return another's points, and it lives in the injection suite beside the cross-tenant `404`.

**The part a future maintainer would delete as redundant is the IDF correction.** With sparse vectors under payload partitioning, inverse-document-frequency statistics are computed shard-wide: every Tenant's vocabulary blends into one set of term frequencies. Payload filtering isolates *results*, not *statistics*. So a term that is rare in one Tenant's Corpus is scored against a population that includes another Tenant's documents — a cross-tenant influence on ranking, present even though no foreign point is ever returned. It is invisible to a test that only checks which points came back, which is precisely why it needs writing down. Qdrant exposes an `idf` search parameter to narrow the population it computes over; the fix is to set it, demonstrate the effect before and after, and pin it with a test that fails if the parameter is removed.

The cost accepted is that the demonstration is only meaningful with more than one Tenant's material in the index, so the ablation and isolation fixtures must carry two — a single-tenant index would make every one of these tests pass for the wrong reason.
